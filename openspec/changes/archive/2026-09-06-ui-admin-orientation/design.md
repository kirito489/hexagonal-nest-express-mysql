## Context

`/members` 的實體是 `MemberRecord`（`members` 表），管的是能登入後台的帳號。
權限碼是 `BACKEND:ACCOUNT:*`——**碼本身用的是 ACCOUNT，不是 MEMBER**。
所以「帳號」才是這個領域一路以來的用字，「會員管理」是 UI 層自己長出來的。

首頁 `routes/home/page.tsx` 目前有兩張卡：一張佔位文字、一張個人資料。
`openspec/specs/` 底下**沒有任何 capability 涵蓋首頁**。

模板的前台側（`/api/front/*`）目前只有 `ping`，沒有第二個帳號體系。

## Goals / Non-Goals

**Goals:**

- 同一個東西在四個地方叫同一個名字。
- 登入後的第一個畫面描述的是現在的狀態，不是兩個版本以前的。
- 首頁有 spec 覆蓋，下一次它過期時有東西會發現。

**Non-Goals:**

- **不新增前台會員管理。** 藍本的分組問題來自它有兩個帳號體系，本模板沒有。
- **不做營運摘要 / 儀表板**（D3）。
- 不動權限碼、路由、API 契約。

## Decisions

### D1：命名統一為「管理者帳號」，而不是「帳號管理」

兩個候選：

| 候選 | 優點 | 代價 |
| --- | --- | --- |
| 帳號管理 | 對齊既有的 `PERMISSION_CATALOG`，**不必重跑 seed** | 衍生專案加了前台會員之後仍要再改一次名 |
| **管理者帳號** ✅ | 語意不含糊，**「管理者 / 會員」是操作者腦中真正的區分** | 要改 `PERMISSION_CATALOG` 的 `name`，部署需重跑 seed |

選後者。這是**模板**——衍生專案幾乎一定會長出前台使用者，
而那時「帳號管理」與「會員管理」的歧義會再次出現。
現在付一次 seed 的代價，換掉一個註定要再改的名字。

`db:seed` 是 `alwaysRun` 的 upsert，重跑安全，代價只是要記得跑。
寫進 proposal 的 Impact 與 `tasks.md` 的驗證段。

### D2：分組名改依「管理誰」，並把判準寫進 spec

「使用者與權限」把**對象**（使用者）與**機制**（權限）並列在同一個名字裡，
所以它無法回答「這一組是關於誰的」。改成「管理者與權限」。

**判準要寫進 `platform-frontend-conventions`**：group 名稱依「管理的對象」命名，
而不是依「功能的種類」。現況的規範只說「依 group 分組渲染」——
**沒有說 group 該怎麼切，而這次的問題正是切錯了維度**。

沒有守則能擋分組命名，這條是自律；但寫下來至少讓下一個人有依據。

### D3：首頁不做營運摘要

藍本的首頁改成「營運概況」，因為它有 `GET /moderation/dashboard` 這支現成的快照端點。
**本模板沒有任何統計端點。**

三個選項：

| 做法 | 問題 |
| --- | --- |
| 新增統計端點 | 這支 change 是 UI 導覽，不是新功能。而且要先決定「統計什麼」，模板沒有領域可統計 |
| 放假資料 / 佔位圖表 | **比現在的佔位文字更糟**——現在的至少誠實地說「骨架已建立」 |
| **只留真正屬於首頁的內容** ✅ | 個人資料（Sidebar 給不了）+ 一句說明這個帳號的權限範圍 |

首頁**刻意不放功能捷徑**：Sidebar 常駐且不可收起，再列一次是純粹的重複。

### D4：首頁的內容依權限決定，而不是寫死

個人資料對所有登入者都成立（`/me` 不需要額外權限）。
若未來加了需要權限的區塊，**沒有權限就整塊不渲染**，
而不是渲染一個空的或錯誤的卡片。

這條現在沒有實際的區塊在用，但它是 `ui-home` 存在的理由之一：
下一個往首頁加東西的人，需求就在那裡等著。

### D5：`ui-home` 是新 capability，不是塞進既有的

首頁不屬於 `ui-member-management` 也不屬於 `platform-frontend-conventions`
（後者是跨頁的慣例，不是某一頁的行為）。

它至今沒有 spec，正是那句佔位文字能過期而沒人發現的原因——
**沒有需求，就沒有東西會過期**。

## Risks / Trade-offs

- **[改名要重跑 seed]** → `db:seed` 是 upsert，重跑安全。風險是**忘記跑**：
  忘了的話 DB 裡還是舊的 `name`，而權限樹顯示的是 DB 的值——
  畫面會出現「管理者帳號」的群組標題配「後台-帳號管理-檢視」的項目名。
  已寫進 `tasks.md` 的驗證段與 proposal 的 Impact。
- **[操作面的 BREAKING]** → 熟悉舊介面的人會撞一次肌肉記憶。舊用法本來就是錯的。
- **[分組判準是自律]** → 沒有守則能擋分組命名。寫進 spec 至少讓下一個人有依據。
- **[C6c 的守則擋不住這次的漂移]** → 這正是本 change 的起因：
  `permission-codes-sync.spec.ts` 檢查「對照是否齊全」，
  **兩邊都在但用詞不同時它全綠**。這個限制在 C6c 就寫下來了，
  只是當時沒發現模板已經處在那個狀態。本 change 不新增守則來擋它——
  要擋得住得比對「sidebar label ↔ 權限樹 module label」，
  而那兩者本來就不必然相同（一個是頁面名、一個是模組名）。**改為靠 spec 明文與人。**

## Migration Plan

1. 改四處字串。
2. **重跑 `pnpm --filter @app/api db:seed`** 讓 DB 的 `name` 同步。
3. 無 migration、無 API 契約變更。
