## Context

權限樹的資料來自 `GET /api/admin/roles/permissions`，回的是扁平陣列，每筆帶
`permissionCode` / `name` / `platform` / `module` / `action`。
`group-permissions.ts` 依 `platform → module` 分組，並把同 module 的 VIEW / EDIT
收進同一個 `ModuleGroup`。

`PermissionsField` 目前直接渲染 `platform.platform` 與 `g.module`——
也就是**碼片段本身**。項目則渲染 `view.name` / `edit.name`，那是後端目錄的
`name`（「後台-帳號管理-檢視」）。

安全管理三頁（IP 白名單 / IP 黑名單 / 帳號鎖定）走 `@Roles(RoleCode.SUPERADMIN)`，
**沒有權限碼**，所以整個 module 不在那個 API 的回應裡。

## Goals / Non-Goals

**Goals:**

- 權限樹一眼讀得出「這個角色能做什麼」。
- 「後台有這頁、權限設定裡卻找不到」這個疑問在畫面上當場被回答。
- 「什麼時候 disabled、什麼時候隱藏」有單一答案且寫進 spec。

**Non-Goals:**

- **不改安全模型。** 不新增 `BACKEND:SECURITY:*`、不改 `SecurityController`
  的守衛。這支只讓既有決定變得可見。
- **不改 `PERMISSION_CATALOG` 的 `name`**（見 D5）。
- 不動 `ATTACHMENT` 的權限碼（D4）。

## Decisions

### D1：中文對照放前端，用守則擋漂移

不讓 API 多回一個 `moduleLabel` 欄位：那個標籤只有這一個畫面在用，
為它改 swagger + 重跑 api-client 不划算，而且 `platform` / `module`
是**碼的結構**，中文名是**顯示層的事**。

代價是同一份分類法存在前後兩處。由 api 側守則雙向比對 `PERMISSION_CATALOG`：
缺對照要紅，**有多餘的對照也要紅**（權限碼移除後留下的死字串）。

⚠️ 守則以正規式讀常數的字面值，所以**對照表必須維持字面物件的寫法**。
這一點要寫進檔頭警告——與 `permission-codes.ts` 同樣的約束（C6b 已建立此模式）。

查不到對照時**退回原始碼片段而非空字串**：標題空白的卡片看起來像壞掉，
英文標題至少還讀得出是哪一組。

### D2：項目顯示動作，不再顯示目錄的 `name`

群組標題變中文之後，項目名「後台-帳號管理-檢視」把標題的內容又講了一次
——三層裡有兩層是重複的。改為顯示「檢視」/「編輯」。

**不需要第三份對照表**：`ModuleGroup` 已經是按 action 分好的
（`group.view` / `group.edit`），要顯示的字直接綁在那個結構上。
再開一份 `ACTION_LABELS` 等於為兩個固定值建一張表，還多一個會漂移的地方。

`name` 仍由 API 回傳、仍存在型別裡，只是權限樹不再顯示它。
不從 `ResolvedPermission` 移除：那是後端契約的一部分，
移掉會讓下一個要用它的人以為後端沒回。

### D3：安全管理畫成「不可指派」區塊，不新增權限碼

三個選項：

| 做法 | 問題 |
| --- | --- |
| 新增 `BACKEND:SECURITY:*` | **改變安全模型**。能改 IP 名單等同能繞過所有 IP 層防護，不存在「只給一半」的合理情境 |
| 維持現狀（不顯示） | 使用者合理地判斷成「權限漏設了」，而沒有任何地方回答他 |
| **顯示為不可指派** ✅ | 當場回答那個問題，且不動任何守衛 |

區塊**不放 checkbox**（不是 disabled 的 checkbox）：disabled 的勾選框仍在說
「這是一個可以勾的東西，只是你現在不能勾」，而它對任何人都不能勾。
改成純說明列表 + 一句話講**為什麼**——只寫「無權限」的話使用者會去要那個權限，
而它要不到。

措辭刻意不提「已授予 / 未授予」：它描述的是**指派機制**而非某個角色的狀態，
所以不論在看哪一個角色（含超級管理者）都成立。

⚠️ 這份清單寫死在前端，**正確性依賴後端沒有改用 `PermissionsGuard`**。
改了的話畫面會繼續說「不可指派」而它已經可以指派了——**畫面對使用者說謊，
且不會有任何測試失敗**。所以守則要盯住那個守衛（見 D6）。

### D4：`ATTACHMENT` 留在樹上，且不加「尚無對應頁面」的註記

`BACKEND:ATTACHMENT:EDIT` 確實在保護附件端點，只是 `apps/web` 還沒有附件頁，
所以勾了看不出差別。**不從權限樹移除**：它保護的東西是真的。

也**不寫「（尚無對應頁面）」之類的 UI 文字**——那會隨功能上線而過期，
卻沒有任何東西會提醒你回來改它。這個脈絡寫在對照表的註解裡，給讀程式碼的人。

### D5：不改 `PERMISSION_CATALOG` 的 `name`——藍本這一段不適用

衍生專案這支 change 有「權限名稱對齊側邊欄命名」的一整塊，
起因是它的 `improve-admin-orientation` 把側邊欄改成「管理者帳號」「會員列表」
而權限目錄沒跟上。

**本模板沒有那個漂移**：側邊欄是「帳號管理」「角色管理」，
目錄是「後台-帳號管理-*」「後台-角色管理-*」，兩邊一致。

照抄會改到 DB 的顯示字串、需要重跑 `db:seed`，而**解決的是一個不存在的問題**。
不做。

> ⚠️ 給 C6d（`ui-admin-orientation`）的提醒：那支若改了側邊欄用語，
> **`MODULE_LABELS` 與 `PERMISSION_CATALOG` 的 `name` 都要一起改**，
> 否則就會在本模板複製出衍生專案那個漂移。守則擋得住「對照缺漏」，
> **擋不住「兩邊都在但用詞不同」**。

### D6：兩條守則都放 C6b 建立的那支檔案

`permission-codes-sync.spec.ts` 已經在 api 側、已經能讀 `apps/web` 的原始碼、
已經有「掃描範圍有效」的自我保護。新增的兩條是同一個關切
（**前端寫死的後端知識必須跟得上後端**），放同一支檔案而不是再開一支。

第二條守則刻意**只驗守衛存在、不比對條目內容**（「IP 白名單 / IP 黑名單 / 帳號鎖定」
三個字串）：比對它們需要第三份「端點 → 中文名」的對照，
而擋下的只是文案不精確。判定前**必須先去除註解**——
把裝飾器註解掉是最典型的「停用但留著」，而 `// @Roles(...)` 會把不去註解的
正規式餵飽，規則就永遠是綠的。

### D7：`disabled` 與隱藏的分界依「控制項的層級」而非「原因的種類」

實作已經是對的（`RolesTable` 用 `{canEdit && …}` 隱藏、用 `DisabledHint` +
`disabled` 表示資料狀態），spec 卻寫著二選一。把實作的規則寫成明文：

- **列內動作**（dropdown 裡的編輯 / 刪除）因**權限不足**時**隱藏**。
  一列可能有多個動作，把要不到的權限逐列 disabled 給人看沒有意義，只是噪音。
- **因資料狀態**不允許時 **disabled + tooltip 說明原因**
  （「預設角色不可編輯」「角色有 N 位使用者」）——那是可以改變的狀態，
  使用者需要知道差在哪。

C6a 已經用過這個分界（已到期的鎖定列用 disabled 而非隱藏），
這裡把它從「兩支 change 的共同做法」升格成明文規則。

## Risks / Trade-offs

- **[中文對照與後端目錄是兩份真相]** → 守則雙向比對擋住缺漏與死條目，
  但擋不住「兩邊都在但用詞不同」（D5 的提醒）。
- **[不可指派清單寫死在前端]** → 由 D6 的守則盯住後端守衛。守則抓得到
  「守衛被拿掉」，抓不到「清單漏了新的安全頁面」——新增 SUPERADMIN-only 頁面時
  要記得補。這個限制寫進需求。
- **[項目不再顯示目錄 `name`]**（D2）→ 若未來目錄的 `name` 帶了額外資訊
  （例如註記），權限樹看不到。目前 `name` 只是「平台-模組-動作」的組合，沒有額外資訊。
- **[spec 行為修正可能與既有測試衝突]** → 實作本來就是那樣，spec 才是錯的。
  若有測試斷言「dropdown 整個不顯示」，那條測試也是錯的，要一起改。

## Migration Plan

無 migration、無 API 契約變更、**不需要重跑 seed**。純前端顯示調整加兩條守則。
