## ADDED Requirements

### Requirement: 權限模組的中文對照必須齊全且無死條目

架構檢查 SHALL **雙向**比對前端的中文對照表與後端 `PERMISSION_CATALOG`：

- 目錄裡的每個 `platform` 與 `module` MUST 在對照表中有中文名。
  缺對照時群組標題會退回英文碼片段——**畫面不會壞、不會報錯，
  只有一張卡片長得跟別人不一樣**。
- 對照表中沒有對應權限碼的條目 MUST 被視為違規。那是權限碼移除後留下的死字串，
  沒有人會注意到它還在。

只檢查單向（缺對照）會讓對照表單向膨脹，而膨脹的部分正好是最沒人看的地方。

檢查 MUST 先斷言「解析得出東西」（對照表讀得到、解出的鍵數量大於零、
後端目錄非空），否則正規式或常數寫法一變，規則會靜默空轉成「全部通過」。

#### Scenario: 後端新增模組

- **WHEN** `PERMISSION_CATALOG` 加了新的 module 而前端沒有補對照
- **THEN** 檢查失敗，訊息指出缺的是哪個 module、來自哪個權限碼

#### Scenario: 權限碼移除後的死字串

- **WHEN** 某個 module 從目錄移除，而對照表仍留著它的中文名
- **THEN** 檢查失敗，訊息指出該條目沒有對應的權限碼

### Requirement: 不可指派清單必須與後端守衛一致

權限樹寫死了一段「安全管理不可指派」的說明，其正確性完全依賴
`SecurityController` 仍以 `@Roles(RoleCode.SUPERADMIN)` 保護。
架構檢查 SHALL 確認那個守衛仍然存在。

**改用 `PermissionsGuard` 的話，前端會繼續顯示「不可指派」而它已經可以指派了**
——畫面在對使用者說謊，且不會有任何測試失敗。

判定 MUST 先去除註解。把裝飾器註解掉是最典型的「停用但留著」，
而 `// @Roles(RoleCode.SUPERADMIN)` 會把不去註解的正規式餵飽，規則就永遠是綠的。

本規則 SHALL **只驗守衛存在，不比對清單的條目內容**。比對「IP 白名單 /
IP 黑名單 / 帳號鎖定」三個字串需要第三份「端點 → 中文名」的對照，
而擋下的只是文案不精確。

⚠️ 因此本規則**抓不到「新增了 SUPERADMIN-only 頁面卻忘了補進清單」**。
這是刻意的範圍限制，不是待補的缺口。

#### Scenario: 守衛被改掉

- **WHEN** `SecurityController` 不再有 `@Roles(RoleCode.SUPERADMIN)`
- **THEN** 檢查失敗，訊息指出前端有一段寫死的說明需要同步移除

#### Scenario: 守衛被註解掉

- **WHEN** 該裝飾器被 `//` 註解但仍留在檔案裡
- **THEN** 檢查同樣失敗——判定前已去除註解
