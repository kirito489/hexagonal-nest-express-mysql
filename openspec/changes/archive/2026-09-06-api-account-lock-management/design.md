## Context

帳號鎖定的機制早就完整：登入失敗計數 → 達門檻寫 `members.locked_at` →
`APPLICATION_ACCOUNT_LOCK_DURATION_MIN` 之後自動到期 →
`POST /api/admin/security/unlock-account` 可提前解鎖。

**唯一缺的是「看得到」。** 這支只補那一塊，並刻意把 `tasks/todo.md` 記載的範圍縮小
——縮小的理由要寫下來，否則下一個讀 todo 的人會以為有人做漏了。

既有結構的兩個關鍵事實：

- 鎖定狀態**不是獨立的表**，就是 `members.locked_at` 這一個時間戳。
- 「還鎖著嗎」是**即時算的**（`lockedAt + DURATION_MIN`），刻意不另存到期欄位——
  存了的話調整設定不會影響既有紀錄，會出現「設定顯示 15 分鐘、實際 60 分鐘」
  的不一致，直到那批紀錄自然消失。

## Goals / Non-Goals

**Goals:**

- 管理員能看到「現在有誰被鎖著」，不必等使用者來反應。
- 列表上的「鎖定中 / 已到期」判定與登入時的判定**是同一份規則**（D3）。
- 功能停用時畫面要講得出「不會有」，而不是「目前沒有」（D6）。

**Non-Goals:**

- **不新增解鎖端點**（D1）。
- **不做手動鎖定**（D2）。
- **不建鎖定歷史表**——目前沒有「這個人這個月被鎖過幾次」的需求，
  為它建一張表是先做了再找用途。
- **不改 `APPLICATION_ACCOUNT_LOCK_ENABLED` 的預設值**。要不要預設開啟是
  獨立的安全決定，夾帶在一個「加一頁列表」的 change 裡不對等。

## Decisions

### D1：不新增 `DELETE /locks/:id`，解鎖沿用既有端點

todo 記載的範圍含 `DELETE …/:id`。不做，因為它與
`POST /api/admin/security/unlock-account` **是同一個動作**，差別只在吃 id 還是 email
——而列表頁本來就會拿到 email。

**兩支做同一件事的端點，代價不是多一支程式碼**：它們會各自演化
（一支加了稽核、另一支沒有），而呼叫端要選一個，選錯了不會有人發現。

也考慮過反過來——用 `DELETE /locks/:id` 取代舊端點，讓 REST 語意一致。
不選，因為那要推翻 `api-security-management` 已寫入的端點契約，
而**那支端點是為了解決「帳號鎖定沒有復原路徑」才加上的**。
為了語意整齊而動它，收益不成比例。

### D2：不做手動鎖定（`POST /locks`）

手動鎖定要回答一個問題：它跟停用帳號（`status = false`）差在哪？

| | 鎖定 | 停用 |
| --- | --- | --- |
| 誰觸發 | 系統（登入失敗達門檻） | 管理員 |
| 怎麼結束 | **時間到自動解開** | 管理員再打開 |
| 意圖 | 擋暴力破解 | 擋這個人 |

管理員按下「鎖定」時的意圖幾乎一定是後者，而他拿到的是前者——
**一個 N 分鐘後自己失效的封鎖**。那不是少一個功能，是給錯工具。

### D3：到期判定必須與登入路徑共用同一份規則

`members.locked_at` 只是時間戳，「還鎖著嗎」要靠
`lockedAt + APPLICATION_ACCOUNT_LOCK_DURATION_MIN` 算。那個計算目前在
`PrismaAccountLockAdapter.checkLock`。

**列表不得自己算一次。** 兩份計算會漂移，而漂移的症狀是
「列表說鎖著、但那個人登得進去」——看起來像資料不同步，實際是兩份規則。

實作上列表不可能逐列呼叫 `checkLock`（N+1），所以共用的不是那個方法，
而是**它背後的那條規則**：抽出一個計算「到期時間」的純函式，
`checkLock` 與列表查詢都用它。列表用它換算出一個 SQL 可用的分界時間戳
（`lockedAt >= now - durationMs` 即為鎖定中），逐列的 `status` 與 `unlocksAt`
也由它算——**同一個函式的三種用法，而不是三份規則**。

列表查詢放進 `AccountLockPort`（同一個 adapter 實作），不是塞進 member 的持久層
port：那條規則屬於鎖定，不屬於會員。

### D4：列表預設只顯示「鎖定中」，但「已到期」查得到

`locked_at != null` 的列包含**已經到期、只是還沒被清掉**的帳號
（清除發生在下次登入或解鎖時）。這些人現在登得進去，把他們列成「鎖定中」是錯的。

- 預設過濾為**鎖定中**——管理員打開這一頁時問的是「現在有誰被鎖著」。
- 但保留 `status=expired` / `all` 讓「這個人今天被鎖過」查得到。
  沒有鎖定歷史表，這是唯一能回答那個問題的地方。
- 每一列 MUST 顯示狀態，MUST NOT 只顯示 `lockedAt` 讓人自己心算。

### D5：已到期的列**仍然**提供解鎖——與衍生專案相反

**藍本在這一點上不能照抄。** 衍生專案的 `UnlockAccountService` 是
`if (lockStatus !== 'LOCKED') throw`，所以它的前端把已到期的列設成 disabled。
本模板的同一支服務是 `if (status === 'NONE') throw`——**EXPIRED 刻意放行**，
原始碼註解寫明理由：`lockedAt` 仍有值、Redis 的失敗計數也可能還在，
而清掉那些殘留正是管理員按下解鎖時的意圖。

那段差異來自 `platform-security-hardening`（C2），衍生專案在那之前就分支了。

更關鍵的是：列表只列 `lockedAt != null` 的帳號，**`NONE` 不可能出現在列表上**
——因此列表上每一列的解鎖都會成功。照抄藍本會做出一顆
**擋住有效操作的 disabled 按鈕**，而那個操作正是這一頁存在的理由之一。

已到期的列仍要標示狀態，但那是**說明**而非阻擋：讓管理員知道
「這個人已經可以登入了，按解鎖是清掉殘留紀錄」，而不是以為按了會放行誰。

這件事的教訓不在這一頁：**回補藍本時，前端的每一個 disabled / 隱藏條件
都要回頭確認它依據的後端規則在本專案是否成立**。前端測試不會發現——
它驗的是「expired 時 disabled」，而那條斷言本身就是錯的前提。

### D6：回應要帶 `lockEnabled`

衍生專案在實機驗收時才發現：把一個帳號的 `locked_at` 設成兩分鐘前、再用它登入
——**登入成功了**。原因是 `APPLICATION_ACCOUNT_LOCK_ENABLED` 預設 `false`，
而 `LoginService` 檢查鎖定、記錄失敗、寫入鎖定三處**全部包在那個 flag 底下**。

也就是說：**預設部署下系統永遠不會產生鎖定紀錄**，這一頁會永遠是空的，
而空狀態寫著「目前沒有帳號被鎖定」——那在此時是**錯的**。
不是沒有人被鎖，是根本不會鎖，而兩者在畫面上長得一模一樣。

修法是讓列表端點回傳 `lockEnabled`，前端據此顯示停用提示。
**不另開一支 flag 端點**：需要這個值的只有這一頁，而它本來就要呼叫這支；
前端目前也沒有任何讀取 feature flag 的管道，為此建一套基礎設施
比問題本身大得多。

**這件事驗收前看不出來**——單元測試、e2e、型別全都會過，
因為它們驗的是「列表正確反映 `locked_at`」，而那是對的。
錯的是「`locked_at` 從哪來」這個前提。所以 `tasks.md` 的驗證段
**必須含一次把 flag 開起來的實機確認**，不能只跑測試。

### D7：頁首用 `@/components/PageHeader`，不照抄既有頁面

衍生專案的這一頁正是「照抄前一頁抄歪」的那一頁：多了內距、頁首用 `<div>`
而非 `<header>`、標題字重 `font-bold` 而非 `font-semibold`——**三處偏差、
typecheck / lint / 測試全綠**，是用眼睛看出來的，事後另開 `e674a2a` 修。

本模板已把那段結構收斂成 `PageHeader` 元件。這一頁用它，
**沒有可以寫歪的地方**。副標的兩種措辭（見下）用 `description` 傳入。

副標描述的是**啟用後**的行為，所以功能關閉時不能用現在式陳述——
「連續登入失敗會自動鎖定」與底下的停用提示會直接互相矛盾，
而使用者只會讀到其中一句。關閉時改成中性的說明，狀態交給提示區講。

## Risks / Trade-offs

- **[範圍比 todo 記載的小]** → 已在 proposal 與 D1 / D2 寫明理由，
  並會在 todo 的完成紀錄裡註明「D1 / D2 縮小了範圍」，避免看起來像做漏。
- **[這一頁在預設設定下是空的]** → 帳號鎖定預設關閉。已用 `lockEnabled` +
  停用提示讓它看得出來；要不要預設開啟是另一個決定，不在本 change 範圍。
- **[沒有鎖定歷史]** → `locked_at` 被清掉之後那次鎖定就消失了。D4 的「已到期」
  查詢能涵蓋「清掉之前」的窗口，但不是完整歷史。真的需要時要另建表，
  屆時本頁是自然的入口。
- **[新增 endpoint 需要 `swagger:bundle` + `api-client generate`]** → 漏跑會讓前端
  拿不到型別。`swagger-sync.spec.ts` 會擋路由層級的漂移，`swagger:check` 擋內容層級。
- **[抽出到期計算會動到既有的 `checkLock`]** → 那是登入路徑上的程式碼。
  重構後 `LoginService` 與 adapter 的既有測試必須全綠且**不修改斷言**——
  要改斷言就代表行為變了，那不是重構。

## Migration Plan

無 migration。新增一支唯讀端點與一個前端頁面，既有契約不動。
